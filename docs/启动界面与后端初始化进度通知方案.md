# 启动界面与后端初始化进度通知方案

## 1. 背景

Panes 当前已经具备完整的启动初始化流程：

1. 前端完成事件监听后，发送 `ssh-remote-project-session-sync-ready` 事件。
2. 后端恢复所有已启用的 SSH 连接及 CLI 隧道。
3. 后端启动并登记各 SSH 远端 CLI 服务。
4. 后端同步 SSH 远端项目会话。
5. 后端按工作区通知前端重新读取本地数据库中的会话。

现有问题不是缺少后端初始化流程，而是前端主界面在后端初始化完成前已经展示，并提前读取远端 CLI 的模型和健康状态。此时远端 CLI 服务可能尚未登记，前端会把启动过程中的临时状态保存为“CLI 不可用”，从而在跨 CLI 会话切换时显示“SSH 远端 CLI 服务未在启动阶段登记”。

## 2. 目标

在不重构现有 SSH、CLI 服务和远端会话同步逻辑的前提下，增加一个应用启动界面：

- 应用启动后先显示启动界面，不立即显示主界面。
- 启动界面以较大的“启动中”作为主标题。
- 主标题下方以较小文字显示后端当前正在执行的初始化阶段。
- 后端进入现有启动流程的每个主要阶段时，向前端发送进度事件。
- 后端现有启动流程全部执行结束后，向前端发送启动完成事件。
- 前端收到启动完成事件后，读取最新的 CLI、模型、健康状态和会话数据，然后进入主界面。
- 单个 SSH 连接、CLI 服务或远端项目同步失败，只记录现有失败状态并继续启动流程，不得阻止进入主界面。

启动完成表示“所有启动任务都已经执行并得出结果”，不表示“所有远端连接和 CLI 都必须成功”。

## 3. 不在本次范围内的内容

- 不重写 `init_all_ssh_remote_server`。
- 不重写 `refresh_all_ssh_remote_project_sessions`。
- 不改变 SSH Tunnel Lifecycle 的职责。
- 不改变 CLI Service Lifecycle 的职责。
- 不改变各 CLI 客户端实现层的职责。
- 不要求所有远端连接成功后才能进入主界面。
- 不删除前端用于页面渲染的引擎、模型、健康状态和用量状态。
- 不增加新的数据库表或数据库迁移。

## 4. 现有代码链路

### 4.1 前端启动入口

`src/main.tsx` 完成语言、主题和显示缩放初始化后渲染 `App`。

`src/App.tsx` 当前会立即渲染主界面，同时异步执行：

- 加载工作区；
- 加载当前工作区的引擎目录；
- 读取本地或 SSH 远端项目的缓存会话；
- 注册远端会话刷新事件；
- 发送 `ssh-remote-project-session-sync-ready` 事件，通知后端开始 SSH 远端初始化。

其中，当前工作区引擎目录的读取可能早于后端 CLI 服务登记完成，这是本次问题的直接触发点。

### 4.2 后端启动入口

`src-tauri/src/lib.rs` 已监听 `ssh-remote-project-session-sync-ready`，收到事件后依次执行：

1. `ssh::cli_tunnel_registry::init_all_ssh_remote_server`；
2. `remote_project_session_refresh_service::refresh_all_ssh_remote_project_sessions`。

第一步负责：

- 读取所有启用的 SSH 连接；
- 检测 SSH 连通性；
- 扫描远端可用 CLI；
- 为各 CLI 建立并登记 SSH 隧道。

第二步负责：

- 遍历所有启用的 SSH 远端项目；
- 通过 `cli_service_lifecycle::set(connection_id, cli_id)` 启动并登记 CLI 服务；
- 调用各 CLI 的会话查询能力；
- 将远端会话写入本地数据库；
- 发送 `ssh-remote-project-sessions-refreshed` 事件，通知前端重新读取对应工作区的会话。

上述流程已经具备逐连接、逐工作区和逐 CLI 的失败后继续能力。本次只在现有流程周围增加进度通知和最终完成通知。

## 5. 启动界面

启动界面覆盖应用主内容区域，启动完成前不渲染可操作的主界面。

界面内容保持简单：

```text
启动中

正在加载基础数据……
```

随着后端阶段变化，小字依次更新，例如：

```text
启动中

正在建立 SSH 连接……
```

```text
启动中

正在建立远端 CLI 隧道……
```

```text
启动中

正在启动远端 CLI 服务……
```

```text
启动中

正在同步远端会话……
```

收到启动完成事件后，启动界面退出并显示现有主界面。

## 6. 启动进度事件

新增一个统一的启动进度事件，建议事件名为：

```text
app-startup-progress
```

事件只传递启动界面实际需要的数据：

```ts
interface AppStartupProgressEvent {
  phase:
    | "loading-base-data"
    | "connecting-ssh"
    | "creating-cli-tunnels"
    | "starting-cli-services"
    | "syncing-remote-sessions"
    | "completed";
  message: string;
}
```

`phase` 用于前端判断是否完成，`message` 直接用于启动界面的小字显示。本次不增加百分比、任务数量或复杂的任务状态管理。

## 7. 前后端执行顺序

### 7.1 前端

1. 渲染启动界面，初始提示为“正在加载基础数据……”。
2. 注册 `app-startup-progress` 监听。
3. 注册现有的远端会话刷新监听。
4. 完成必要的基础数据读取。
5. 确认所有启动相关监听已经注册后，发送现有的 `ssh-remote-project-session-sync-ready` 事件。
6. 启动完成前，不加载 SSH 远端工作区的引擎目录、模型和健康状态。
7. 收到 `phase = completed` 后，直接从后端读取当前工作区的最新引擎目录、模型和健康状态。
8. 退出启动界面，显示现有主界面。

### 7.2 后端

后端收到现有的 `ssh-remote-project-session-sync-ready` 后：

1. 发送“正在建立 SSH 连接……”事件。
2. 执行现有 `init_all_ssh_remote_server`。
3. 在隧道登记阶段发送“正在建立远端 CLI 隧道……”事件。
4. 开始远端项目刷新前发送“正在启动远端 CLI 服务……”事件。
5. 开始查询并持久化远端会话时发送“正在同步远端会话……”事件。
6. 所有现有启动任务执行结束后，无论其中是否存在失败，都发送 `completed` 事件。

顶层初始化失败也必须进入统一结束路径并发送 `completed`，不能让启动界面永久停留。

## 8. 失败处理

现有失败处理规则保持不变：

- SSH 连接失败：记录连接失败状态，继续处理其他连接。
- 某个 CLI 隧道建立失败：记录该 CLI 失败，继续处理其他 CLI。
- 某个 CLI 服务启动失败：记录该 CLI 失败，继续处理其他 CLI。
- 某个远端项目会话同步失败：记录失败并通知前端，继续处理其他项目。
- 全部任务执行结束：始终发送启动完成事件并进入主界面。

进入主界面后，失败的连接和 CLI 继续使用现有界面展示失败状态及重连能力。

## 9. 前端状态说明

前端现有 `engineStore` 保存的是页面展示所需的当前数据：

- 引擎及模型目录；
- CLI 健康状态；
- 用量信息；
- 请求加载状态。

SSH 隧道和 CLI 服务生命周期仍全部由后端管理，前端不保存这些生命周期。

本次不删除 `engineStore`。启动界面完成前禁止提前读取远端引擎数据；启动完成后再从后端读取最新结果并写入前端状态用于渲染。这样不会保留后端尚未完成启动时产生的临时“不可用”状态。

## 10. 预计代码落点

### 前端

- `src/App.tsx`
  - 增加启动状态和当前阶段文字；
  - 在启动完成前显示启动界面；
  - 调整现有启动事件监听与 `loadEngines` 的触发顺序；
  - 收到完成事件后加载最新数据并进入主界面。
- `src/lib/ipc.ts`
  - 增加启动进度事件类型和监听函数。
- `src/globals.css`
  - 增加启动界面布局、标题和阶段文字样式。
- `src/i18n/resources/zh-CN/app.json`
  - 增加启动界面中文文案。
- 其他已支持语言的 `app.json`
  - 增加对应启动界面文案，避免出现缺失键。

### 后端

- `src-tauri/src/lib.rs`
  - 在现有启动编排的阶段边界发送进度事件；
  - 在统一结束路径发送完成事件。
- `src-tauri/src/message_notify_helper.rs`
  - 增加启动进度事件的数据结构和发送函数，保持事件契约集中管理。
- `src-tauri/src/ssh/cli_tunnel_registry.rs`
  - 仅在确有需要区分“SSH 连接”和“CLI 隧道”两个显示阶段时发送阶段通知；不改变现有隧道创建逻辑。
- `src-tauri/src/remote_project_session_refresh_service.rs`
  - 仅在现有 CLI 服务启动和会话同步边界发送阶段通知；不改变现有同步逻辑。

## 11. 验收标准

1. Panes 启动后首先显示启动界面，不提前显示可操作的主界面。
2. 启动界面显示较大的“启动中”和较小的当前阶段文字。
3. 后端进入不同初始化阶段时，前端阶段文字随事件更新。
4. 后端启动完成前，前端不会读取 SSH 远端 CLI 的模型和健康状态。
5. 后端完成后，前端读取最新数据并进入主界面。
6. 存在可用 Codex、OpenCode 和 Claude 时，进入主界面后可以在不同 CLI 会话之间切换，不出现“SSH 远端 CLI 服务未在启动阶段登记”。
7. 任意单个 SSH 连接、CLI 或远端项目失败时，启动流程仍能结束并进入主界面。
8. 没有配置 SSH 远端项目时，启动流程也能正常完成并进入主界面。
9. 顶层 SSH 初始化返回错误时，启动界面不会永久停留。
10. 现有 SSH 连接失败、CLI 失败、远端会话同步失败的界面和重试能力保持不变。
