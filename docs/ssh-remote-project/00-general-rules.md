# SSH 远端项目总则

## 一、文档定位

本文档是 `docs/ssh-remote-project` 目录的总则文件，用于固定当前 worktree 的业务定义、阶段边界、实现红线和判定标准。

后续阶段文档、临时方案、口头补充和实现讨论，若与本文档冲突，以用户的最新明确指令为准；在没有新指令覆盖前，以本文档为准。

## 二、项目定义

当前 worktree 名称为：

```text
panes_zh-ssh-remote-project
```

这个名字本身就是当前工作的业务边界。当前 worktree 只处理一条业务路线：

```text
Panes 通过 SSH 连接远端 Linux 机器上的项目
```

这里的“远端”必须指：

- SSH 远端主机；
- 远端项目目录；
- 远端 CLI；
- 远端会话；
- 远端工作区能力。

凡是不属于这条业务路线的代码、设计和运行时，都不属于当前 worktree 的主体范围。

## 三、项目目标

本项目的目标不是新增一套独立的远端页面，而是让远端项目在现有 Panes 结构中具备与本地项目一致的业务入口，并把实际执行目标切换到远端机器。

目标拆解如下：

- 第一阶段：SSH 连接管理。
- 第二阶段：远端项目管理。
- 第三阶段：远端项目工作区基础能力，包括目录树、文件、Git、工作树和终端。
- 第四阶段：远端项目对话能力，通过 SSH 隧道连接远端 CLI 和远端会话。第四阶段剩余工作以计划 5 完成后收口，计划 6 已取消，不执行。
- 第五阶段：远端智能体运行工具。当前状态为暂缓，不作为当前执行项。
- 第六阶段：远端定时任务管理。当前状态为暂缓，不作为当前执行项。

当前阶段判断必须以用户已确认的阶段边界为准，不能因为代码里存在旧能力，就把旧能力误判为当前阶段的一部分。

当前已确认的后续阶段状态：第四阶段剩余工作计划 6 取消；总计划第五阶段“远端智能体运行工具”暂缓；总计划第六阶段“远端定时任务管理”暂缓。后续只有用户重新明确要求时，才重新评估或恢复这些阶段。

## 四、必须先区分的三类路线

后续分析任何函数、设计任何方案之前，都必须先把代码归入以下三类之一：

### 4.1 本地项目路线

指本地工作区、本地仓库、本地文件、本地终端、本地 CLI 的现有业务路线。

### 4.2 本机外部 CLI 服务路线

指：

```text
本机 Panes → 本机 Codex / OpenCode / 其他本机 CLI 服务
```

这类代码里即使出现 `remote` 命名，也不表示 SSH 远端主机，只表示“相对 Panes 进程而言是外部服务”。

### 4.3 SSH 远端项目路线

指：

```text
本机 Panes → SSH → 远端主机 → 远端项目 / 远端 CLI / 远端会话
```

只有这一类，才是当前 worktree 的主体业务。

## 五、当前明确排除项

以下路线不属于当前 `panes_zh-ssh-remote-project` worktree 的实现主体，不能因为名字相似或流程相似，就被当成 SSH 远端项目路线处理：

- 本地项目路线；
- 本机外部 CLI 服务路线；
- 任何“Panes 连本机 Codex app-server / 本机 OpenCode server”的旧实现；
- 任何仅用于本机现有会话发现、恢复、附加的旧实现。

当前明确视为本机外部 CLI 服务路线、不是 SSH 远端项目路线的函数包括：

- `list_codex_remote_threads`
- `attach_codex_remote_thread`
- `list_opencode_remote_sessions`
- `attach_opencode_remote_session`

这些函数当前不能作为 SSH 远端项目实现的主体入口，也不能在当前 worktree 中被误改为 SSH 路线。

## 六、第三阶段与第四阶段边界

### 6.1 第三阶段边界

第三阶段是 SSH 远端开发的基础能力阶段，核心是：

- 远端目录树；
- 远端文件工作区；
- 远端 Git；
- 远端工作树；
- 远端终端切换与使用。

第三阶段已经建立的 SSH 基础链路，是第四阶段的前置条件，不是第四阶段要推翻重做的对象。

### 6.2 第四阶段边界

第四阶段是远端项目对话能力阶段，核心是：

- 远端 CLI 运行时；
- SSH 隧道；
- 远端项目会话刷新；
- 远端项目会话恢复；
- 远端项目消息发送、流式事件和运行时隔离。

第四阶段不能反向污染第三阶段，也不能以“复用旧代码”为理由，把本机外部 CLI 服务路线混入 SSH 远端项目路线。

## 七、SSH 隧道在当前项目中的定位

SSH 隧道在当前项目中是网络层基础设施，不是业务层逻辑。

它的职责只有一个：

```text
把远端主机上的目标能力，稳定映射为本机可连接入口
```

因此，SSH 隧道层只负责这些事情：

- 远端目标的网络可达性；
- 本地端口到远端端口的映射；
- 隧道建立、保活、重连和销毁；
- 向上层提供稳定的本地连接参数；
- 屏蔽远端 IP、SSH 建链和端口细节。

SSH 隧道层不负责这些事情：

- 左侧项目会话列表应该显示什么；
- 某个远端会话属于哪个项目；
- 会话摘要如何写入本地数据库；
- 某个对话业务何时开始、何时结束；
- 具体的消息、模型、权限和运行时业务规则。

在当前项目里，SSH 隧道应被视为“路一直通着”的基础设施层。远端业务能力通过这条路被接到本地，但业务动作本身不属于 SSH 隧道层。

## 八、网络层与业务层的边界

### 8.1 网络层只专注网络层

网络层包括但不限于：

- SSH 连接；
- SSH tunnel；
- `hostId -> cliId -> tunnel` 全局 Map；
- 与 tunnel 相关的生命周期管理。

网络层的职责是：

- 维护这条通路是否存在；
- 提供“本机可连接入口”这个契约；
- 让上层不必关心远端真实地址和网络细节。

网络层不应关心这些业务问题：

- 要不要刷新某个项目的会话；
- 某条会话该不该显示在左侧；
- 某条远端会话对应哪个 `workspace`；
- 某个 CLI 的会话摘要怎么投影到本地 `threads` 表；
- 某个用户动作属于刷新、恢复还是正式对话。

### 8.2 业务层只专注业务层

业务层包括但不限于：

- 远端项目会话刷新；
- 远端项目会话恢复；
- 远端项目对话发送；
- 远端会话摘要同步到本地库；
- 左侧项目和会话的业务归属判断。

业务层的职责是：

- 决定某个用户动作要使用哪台远端主机、哪个 CLI；
- 通过 `hostId + cliId` 从 Map 中获取 tunnel；
- 使用 tunnel 提供的本地入口完成业务动作；
- 把业务结果写回本地数据库或通知界面刷新。

业务层不应关心这些网络问题：

- 远端 IP 是多少；
- 远端真实端口是多少；
- SSH 如何握手；
- tunnel 如何保活；
- tunnel 如何重连；
- tunnel 用的底层协议细节是什么。

### 8.3 单向依赖原则

当前项目必须严格遵守下面这条依赖方向：

```text
业务层依赖网络层提供的入口契约
网络层不依赖业务层规则
```

也就是说：

- 网络层向业务层提供服务；
- 业务层消费网络层能力；
- 业务层不能参与网络层实现；
- 网络层不能承载业务归属判断。

只要某个设计要求业务层去理解 SSH 细节，或者要求网络层去决定业务归属，默认判定为分层错误。

## 九、实现红线

以下内容属于当前项目的红线：

### 9.1 不能动本地路线

凡是本地项目路线、本机外部 CLI 服务路线，都不是本次 SSH 远端项目的改动对象。它们最多只能作为对照参考，不能作为当前实现的承载主体。

### 9.2 不能混淆两种 remote

代码里出现 `remote`，不自动等于 SSH 远端。必须先确认它到底指：

- 本机外部服务；
- 还是 SSH 远端主机。

只要这个判断没完成，就不能继续推导设计结论。

### 9.3 不能让远端失败时回退到本地 CLI

第四阶段的任何对话、会话、运行时或健康检查，只要属于 SSH 远端项目，就必须绑定远端目标。远端失败时，应明确报错，不能偷偷回退到本机同名 CLI。

### 9.4 不能让 SSH 路线改坏主工程本地路线

当前 worktree 的业务目标，与主工程中的本地路线完全不同。未来合并回主工程时，按用户已确认的标准：

```text
如果 SSH 远端项目路线与本地路线发生业务冲突，说明当前实现有问题。
```

“能否无冲突合并回主工程”是当前设计的硬判据，不是可选优化项。

### 9.5 不能为了复用而强行共用业务语义

允许复用纯技术性基础设施，但前提是：

- 不改写本地路线语义；
- 不改变本地路线行为；
- 不把 SSH 远端项目语义塞进本地业务函数；
- 不让主工程已有本地能力为 SSH 远端项目背业务责任。

只要某个“复用”需要先改动本地业务路线，默认判定为方案错误，应先停下确认。

## 十、第四阶段的当前实现基准

第四阶段后续实现，必须从 SSH 远端项目语义出发思考，而不是从旧的本地会话函数出发倒推。

当前基准应是：

```text
workspace
  ↓
sshConnectionId / remote host
  ↓
remote CLI tunnel
  ↓
remote conversation / remote runtime
```

只要一条实现链路的语义起点不是 `workspace -> sshConnectionId -> 远端主机`，就要先怀疑它是否已经偏到本地路线。

## 十一、工作方式约束

当前第四阶段已经返工过一次。时间成本很高，后续实现必须保持高约束、低跑偏。

每次进入具体实现前，都必须先明确三件事：

1. 这一步准备修改哪些文件、哪些函数。
2. 这一步明确不修改哪些文件、哪些函数。
3. 这一步改完以后，用户可见的验收现象是什么。

如果这三件事说不清，就不应直接进入实现。

## 十二、判定标准

后续任何设计或实现，至少要同时满足以下条件，才可视为正确：

1. 业务语义属于 SSH 远端项目路线，而不是本地路线。
2. 第三阶段 SSH 基础能力不被误改或误伤。
3. 本地项目路线和本机外部 CLI 服务路线不被牵连。
4. 远端项目的执行目标始终可追溯到 SSH 远端主机，而不是本机进程。
5. 合并回主工程时，不应与本地路线产生业务冲突。

若上述任意一点不满足，应先停止实现，重新确认边界，而不是继续补丁式推进。

## 十四、远端 CLI 服务复用与项目隔离

### 14.1 固定的全局 Map 结构

SSH tunnel 的全局 Map 固定为：

```text
hostId
  ↓
cliId
  ↓
tunnel
```

这里的 key 只包含远端主机和 CLI 类型，不包含 `workspaceId`、远端项目目录或会话 ID。

同一台远端主机上的同一种 CLI，只维护一条 SSH tunnel 和一个本机连接入口。不能因为同一台主机上有多个远端项目，就为每个项目重复创建 tunnel，也不能把 `projectId` 塞进 tunnel Map 的 key。

### 14.2 服务入口与项目上下文必须分离

远端 CLI 服务入口和项目上下文是两个不同层次：

```text
hostId + cliId
  ↓
一条 tunnel
  ↓
一个远端 CLI 服务入口
  ↓
每次请求携带当前远端项目根目录
  ↓
该项目下的会话
```

远端服务启动时，不绑定、不 `cd` 到任何具体远端项目目录。服务只负责提供对应 CLI 的统一入口；当前项目根目录必须随每一次业务请求传入。

各 CLI 的项目路径传递方式如下：

- Codex：请求携带 `cwd`。
- OpenCode：请求携带 `directory`，或携带 `X-OpenCode-Directory` 请求头。
- Claude：Panes 的 Claude 适配服务每个 `query` 请求携带 `cwd`。

因此，同一台远端主机上的项目 A、项目 B 可以通过同一个 `hostId + cliId` 服务入口并行使用同一种 CLI；项目边界由请求中的远端项目根目录和各自会话决定，不由 SSH tunnel 决定。

### 14.3 生命周期按服务入口统计，不按项目重复建链

远端 CLI 服务的生命周期统计单位是：

```text
hostId + cliId
```

不是：

```text
hostId + cliId + projectId
```

项目 A 和项目 B 同时使用同一台远端主机上的同一种 CLI 时，共用已建立的 tunnel 和已启动的远端 CLI 服务；只增加该服务入口的使用计数或持续会话占用。

只有这个 `hostId + cliId` 不再存在任何一次性业务占用，也不存在任何持续会话占用时，才关闭远端 CLI 服务。关闭服务不等于删除 tunnel；SSH tunnel 仍按网络层规则保留、保活或最终销毁。

### 14.4 架构判定

当前架构不因多项目并发而改为 `hostId + cliId + projectId -> tunnel`。需要按 CLI 分支处理的，仅限于两件事：

- 如何启动和关闭该 CLI 的远端服务；
- 如何按该 CLI 的协议把当前远端项目根目录写入请求。

这属于 CLI 协议适配，不属于 tunnel 架构分裂。业务层仍然只通过 `hostId + cliId` 获取 tunnel 提供的本机入口，不感知 SSH、远端 IP 或远端端口细节。
