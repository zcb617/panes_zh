## 三、业务逻辑冲突文件

以下文件存在业务逻辑冲突，需要逐个确认合并原则，不能只按文本冲突处理。

### 3.0 全局合并核心原则

用户已明确：SSH worktree 中已经定下的“接口、实现类、工厂、业务调用”架构规则，合并回主仓库时必须保留。

这意味着：

```text
业务调用层
  ↓
CliToolFactory
  ↓
CliTool 统一接口
  ↓
Codex / OpenCode / Claude Code 具体实现类
  ↓
本机执行或 SSH 远端执行
```

合并时不能因为主仓库仍是旧写法，就把业务调用重新改回：

```text
业务调用层 → state.engines → 具体 engine
```

主仓库新增的能力，例如电脑操作 SDK、自动更新、图片附件标注、灵活消息撤回和事件修复，需要迁入这套统一 CLI 架构；不能反过来绕开或拆掉 worktree 已定下的接口、实现类、工厂和业务调用边界。

后续判断每个冲突文件时，先看它是否违反这条规则：

- 如果主仓库旧代码直接调用具体 engine，而 worktree 已经改成通过 `CliToolFactory` 获取 `CliTool`，应以 `CliToolFactory + CliTool` 路线为准。
- 如果主仓库新增能力需要某个 engine 能力，应补到 `CliTool` 接口或对应实现类里，而不是让业务调用层重新直接依赖具体 engine。
- 如果 `CliTool` 接口当前缺少主仓库新增能力所需的返回值或参数，应扩展接口契约，而不是回退架构。

### 3.1 `src-tauri/src/commands/chat.rs`

#### 冲突内容

主仓库侧：

- Codex steer 消息仍走 `state.engines.steer_message(...)`。
- 保留 `client_steer_id`。
- 返回 `engine_receipt.expected_turn_id`。
- steer 失败时回滚用户消息。
- 写入 `steer_rpc_failed` / `steer_rpc_accepted` 传输日志。

SSH worktree 侧：

- steer 消息改走 `CliToolFactory`。
- 通过 `CliExecutionContext::from_workspace(&workspace)` 判断本机或 SSH 远端。
- 发送到对应 CLI 工具。
- 远端附件失败时需要清理 `remote_attachment_batch`。
- 远端失败不能回退本机。

#### 业务冲突本质

这是 Codex 继续对话 / steer 消息发送入口冲突，但核心不是“旧 engine 调用”和“新 factory 调用”二选一。

按照本次合并的全局核心原则，`src-tauri/src/commands/chat.rs` 属于业务调用层。业务调用层不应再直接调用具体 engine：

```text
state.engines.steer_message(...)
```

合并后应继续遵守 worktree 已经定下的调用链：

```text
chat command
  ↓
CliExecutionContext::from_workspace(...)
  ↓
CliToolFactory::new(...).create("codex")
  ↓
CliTool::steer_message(...)
  ↓
Codex 本机实现或 Codex SSH 远端实现
```

主仓库这边的 `client_steer_id`、`expected_turn_id`、失败回滚和传输日志是业务能力，不能丢；但这些能力应补进 `CliTool` 接口和 Codex 实现类，而不是让 `chat.rs` 回退到 `state.engines` 旧入口。

#### 合并原则

以 worktree 的统一 CLI 架构为准：

```text
保留 CliToolFactory + CliTool 调用路线
```

同时把主仓库新增或保留的 steer 业务能力迁入该路线：

```text
CliTool::steer_message 需要支持 client_steer_id / receipt 语义
Codex 本机实现继续返回 expected_turn_id
远端实现必须按 SSH 远端目标发送，失败不能本机兜底
chat.rs 继续负责用户消息落库、失败回滚、远端附件清理和日志记录
```

也就是说，3.1 的最终方向不是“合并两段调用代码”，而是：

```text
用 worktree 的接口/工厂/实现类结构承载主仓库的 steer receipt、日志和回滚能力。
```

如果当前 `CliTool::steer_message` 接口返回值不够用，就扩展接口返回值；不允许为了拿 `expected_turn_id` 而绕回 `state.engines.steer_message(...)`。

#### 当前处理结果

已按用户确认的架构红线处理 3.1：

- `chat.rs` 不再回退到 `state.engines.steer_message(...)` 旧入口。
- `chat.rs` 继续通过 `CliExecutionContext + CliToolFactory + CliTool` 调用 Codex。
- `CliTool::steer_message` 接口已扩展，接收 `client_steer_id`、原始文本 `content`，并返回 `EngineSteerReceipt`。
- Codex、Claude Code、OpenCode 三个实现类已同步接口签名。
- Codex 本机实现继续返回 `expected_turn_id`。
- Codex SSH 远端实现通过远端 Codex runtime 调用 `Engine::steer_message`，也返回 `EngineSteerReceipt`。
- `chat.rs` 保留主仓库 steer 失败回滚、`steer_rpc_failed` / `steer_rpc_accepted` 日志和 `expected_turn_id` 返回。
- SSH 远端附件发送失败时仍清理 `remote_attachment_batch`。

### 3.2 `src-tauri/src/engines/codex.rs`

#### 冲突内容

主仓库侧给 `CodexEngine` 增加：

```text
computer_control_service
```

用于电脑操作 SDK / CUA 工具能力。

SSH worktree 侧给 `CodexEngine` 增加：

```text
CodexTransportTarget
Local / WebSocket
```

用于本地 Codex 和 SSH 远端 Codex WebSocket 入口切换。

#### 业务冲突本质

这是 Codex Engine 同时承载电脑操作能力和 SSH 远端传输目标的冲突。

主仓库要求 Codex 支持电脑操作工具；SSH worktree 要求 Codex 能区分本机和远端 CLI 服务。

#### 合并原则

`CodexEngine` 应同时保留：

```text
computer_control_service
+
transport_target
```

本地 Codex：

```text
Local target + 可使用 computer_control_service
```

远端 Codex：

```text
WebSocket target + 远端 CLI 服务
```

不能因为加远端 WebSocket，把主仓库电脑操作工具能力丢掉。

#### 当前处理结果

已按用户确认的架构红线处理 3.2：

- 保留 worktree 的 `CodexTransportTarget`，本机 Codex 和 SSH 远端 Codex 仍由不同 transport target 承载。
- 保留主仓库 Codex 电脑操作所需的 `computer_control_service`、动态工具注册、动态工具调用和授权回收逻辑。
- `CodexEngine::new_remote_websocket(...)` 创建的远端 Codex runtime 不注入电脑操作服务，远端 Codex 不具备本机电脑操作能力。
- `EngineManager::set_computer_control_service(...)` 不再把电脑操作服务全局注入 Codex。
- 新增 `EngineManager::set_local_codex_computer_control_service(...)`，只供 Codex CLI 工具实现类的本机分支调用。
- `CodexCli` 实现类新增 `configure_local_computer_control()`，只在本机 `start_thread`、`send_message`、`steer_message` 分支进入 Codex 前注入电脑操作服务。
- SSH 远端 Codex 分支继续走 `remote_project_codex_runtime_service`，不调用本机电脑操作配置。

### 3.3 `src-tauri/src/engines/opencode.rs`

#### 冲突内容

主仓库侧给 OpenCode 加了：

- `ComputerControlService`
- 本地 callback server
- `callback_cancel`
- `run_dir`
- 本地 OpenCode 电脑操作工具接入

SSH worktree 侧给 OpenCode 加了：

- `OpenCodeTransportTarget`
- `Local / Remote`
- 远端 HTTP endpoint
- 远端事件泵
- `include_directory_header`

#### 业务冲突本质

这是 OpenCode 本地服务生命周期与 SSH 远端 OpenCode 入口的冲突。

主仓库要求本地 OpenCode 能接入电脑操作工具；SSH worktree 要求远端 OpenCode 不启动本机 server，而是使用远端 endpoint。

#### 合并原则

应合成两套路径：

```text
本地 OpenCode：
  start_server(cwd, computer_control_service)
  保留 callback_cancel / run_dir / 本地 child

远端 OpenCode：
  使用 RemoteOpenCodeEndpoint
  不启动本机 child
  使用 directory header / 远端事件泵
```

不能让远端 OpenCode 误启动本机 OpenCode；也不能让本地 OpenCode 丢掉电脑操作工具。

#### 当前处理结果

已按用户确认的架构红线处理 3.3：

- 保留 worktree 的 `OpenCodeTransportTarget`，本机 OpenCode 和 SSH 远端 OpenCode 仍由不同 transport target 承载。
- 保留主仓库本机 OpenCode 电脑操作所需的 `ComputerControlService`、callback server、`callback_cancel`、`run_dir` 和工具写入逻辑。
- `OpenCodeEngine::new_remote_http(...)` 创建的远端 OpenCode runtime 不注入电脑操作服务。
- SSH 远端 OpenCode 的 `ensure_server(...)` 只包装远端 HTTP endpoint、远端事件泵和目录 header，不启动本机 OpenCode child，不创建本机电脑操作 callback server，也不写入本机电脑操作工具目录。
- `EngineManager::set_computer_control_service(...)` 不再把电脑操作服务全局注入 OpenCode。
- 新增 `EngineManager::set_local_opencode_computer_control_service(...)`，只供 OpenCode CLI 工具实现类的本机分支调用。
- `OpenCodeCli` 实现类新增 `configure_local_computer_control()`，只在本机 `start_thread`、`send_message`、运行时目录读取和本机扩展刷新分支进入 OpenCode 前注入电脑操作服务。
- SSH 远端 OpenCode 分支继续走 `remote_project_opencode_runtime_service`，不调用本机电脑操作配置，不回退本机。

### 3.4 `src-tauri/sidecar/claude-agent-sdk-server.mjs`

#### 冲突内容

主仓库侧在 Claude sidecar 请求参数里加入：

- `threadId`
- `computerControlTools`
- Panes computer control MCP server
- 自动把 `mcp__panes-computer-control__*` 加入工具列表

SSH worktree 侧加入：

- `settingSources`
- `strictMcpConfig`
- `enforceApprovalRouting`
- `automaticallyAllowedTools`
- 更严格的审批路由和 MCP 配置控制

#### 业务冲突本质

这是 Claude Code 请求协议同时承载电脑操作工具和 SSH 远端审批 / 配置隔离的冲突。

主仓库需要 Claude 使用电脑操作 MCP；SSH worktree 需要 Claude 在本机/远端项目里按 cwd、审批、MCP 配置正确运行。

#### 合并原则

应保留全部参数：

```text
threadId
computerControlTools
settingSources
strictMcpConfig
enforceApprovalRouting
```

工具列表处理应合成：

```text
基础 allowedTools
+
电脑操作 MCP 工具
+
审批路由开启时，只自动放行不需要审批的工具
```

不能因为远端审批控制把电脑操作 MCP 去掉；也不能因为电脑操作 MCP 绕过审批路由。

#### 当前处理结果

已按用户确认的 CLI 工具架构红线处理 3.4：

- 保留主仓库 Claude Code 电脑操作能力所需的 `threadId` 和 `computerControlTools` 参数。
- 保留 worktree 的 `settingSources`、`strictMcpConfig`、`enforceApprovalRouting` 参数。
- `handleQuery(...)` 仍作为 Claude Code 工具实现链路内的 sidecar 实现细节，不把业务调用层回退到直接依赖具体 engine 的旧路线。
- 电脑操作 MCP server 仍只在收到 `computerControlTools` 后按本次请求创建，并通过 `mcpServers["panes-computer-control"]` 注入 Claude Agent SDK。
- `allowedTools` 合并为统一工具列表：基础工具列表先合入电脑操作 MCP 工具通配符，再根据 `enforceApprovalRouting` 生成自动放行列表。
- `requiresApproval(...)` 明确把 `mcp__panes-computer-control__*` 视为不需要 Claude 通用审批的工具；真实 CUA 调用仍由 Panes 电脑操作代理发起独立授权。
- `canUseTool` 继续保留原有文件写入、网络、工作目录和审批路由检查，不因为电脑操作 MCP 注入绕过远端项目审批边界。


### 3.8 `src-tauri/src/lib.rs`

## 六、下一步处理原则

后续处理冲突时，应遵守以下原则：

1. 以主仓库为底座，保留主仓库已有的电脑操作 SDK、自动更新、图片附件标注、灵活消息撤回和消息处理修复。
