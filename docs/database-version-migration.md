# 数据库版本升级方案

## 1. 方案目标

本方案用于 Panes 本地 SQLite 数据库（当前为 `workspaces.db`）的结构和数据升级。

数据库版本独立于软件版本，从整数 `100` 开始，不使用 `0.65.0`、`0.98.0` 等软件版本号，也不进行软件版本号比较。主仓库 `v0.65.2` 的完整数据库状态被确定为数据库基线 `100`，后续数据库变更从 `101` 开始。

例如：

```text
100.sql
101.sql
105.sql
110.sql
```

版本号可以不连续。程序只按照迁移清单中的顺序执行，不通过 `current + 1` 推算下一版本。

`baseline.sql` 是空数据库初始化脚本，不属于版本迁移清单。它只负责建立主仓库 `v0.65.2` 的业务表结构；建立结构后，再执行 `100.sql` 建立版本表并登记基线版本。

## 2. 数据库版本表

数据库中必须保存一条当前版本记录：

```sql
CREATE TABLE IF NOT EXISTS schema_version (
    id              INTEGER PRIMARY KEY CHECK (id = 1),
    version         INTEGER NOT NULL CHECK (version >= 100),
    migration_file  TEXT NOT NULL,
    applied_at      TEXT NOT NULL
);
```

字段含义：

- `id` 固定为 `1`，保证数据库只有一条当前版本记录。
- `version` 表示最后一次成功执行的数据库迁移版本。
- `migration_file` 保存最近一次成功执行的 SQL 文件名。
- `applied_at` 保存最近一次成功提交的时间。

`100` 表示主仓库 `v0.65.2` 的完整数据库基线。对新数据库，先由 `baseline.sql` 创建这份基线结构，再由 `100.sql` 创建版本表并插入第一条版本记录。`100.sql` 不创建业务表，也不执行其他业务结构变更。当前开发数据库首次接入版本管理时，可以在确认结构就是该基线后登记为 `100`，不能重复执行 `100.sql`。

版本表记录的是“已经完成的版本”，不是“准备执行的版本”。因此，数据库版本为 `100` 时，`100.sql` 已经执行过或已被基线接入确认，启动时必须从迁移清单中 `100` 的下一项开始执行。

## 3. 版本化 SQL 文件

所有数据库变更必须有独立 SQL 文件，文件名直接使用数据库版本号：

```text
src-tauri/src/db/migrations/
  baseline.sql              # 空数据库初始化脚本，不在迁移清单中
  100.sql
  101.sql
  105.sql
  110.sql
```

要求：

- 每一个发生数据库变更的版本对应一个 SQL 文件。
- 一个 SQL 文件只负责一个数据库版本的变更。
- 一次数据库版本升级只能有一个 SQL 文件。一次升级涉及的全部表结构、索引、约束和数据变更，都必须写入该版本对应的同一个 SQL 文件；不得把同一轮功能或同一数据库版本的内部开发步骤拆成多个版本 SQL 文件。
- 文件一旦在用户数据库中执行成功，就禁止修改；修复必须新增更高版本的 SQL 文件。
- SQL 文件中可以包含表结构变更、索引变更、约束变更和数据回填。
- 除建立版本表的 `100.sql` 外，每个 SQL 文件必须在最后写入本版本的 `schema_version` 更新语句；版本号更新属于该 SQL 文件的一部分。
- `100.sql` 是特殊的基线登记文件，只创建 `schema_version` 表并插入版本 `100` 的第一条记录。
- 不能把多个版本合并到一个“最新 SQL 文件”中。
- 不能在启动入口、业务命令或连接初始化代码中直接执行未登记的 `ALTER TABLE`、`CREATE INDEX` 或数据回填。
- 启动代码禁止在 SQL 文件执行完成后另外补写版本号。

如果某个版本必须由 Rust 代码辅助计算数据，仍必须有同版本 SQL 文件，并且 SQL、辅助代码和版本表更新必须属于同一次迁移事务；不能只写一个没有版本文件的代码迁移。

一份完整的 `100.sql` 如下。它只负责建立版本表并登记第一条记录：

```sql
CREATE TABLE IF NOT EXISTS schema_version (
    id             INTEGER PRIMARY KEY CHECK (id = 1),
    version        INTEGER NOT NULL,
    migration_file TEXT NOT NULL,
    applied_at     TEXT NOT NULL
);

INSERT INTO schema_version (id, version, migration_file, applied_at)
VALUES (1, 100, '100.sql', datetime('now'));
```

`101.sql` 及之后的版本更新语句必须是文件的最后一条业务语句。SQL 文件不自行执行 `BEGIN` 或 `COMMIT`，由启动迁移入口统一包裹事务，避免嵌套事务。

## 4. 全局迁移清单

程序中必须有一个唯一的全局迁移清单，清单按数据库版本号升序登记每一项：

```rust
const MIGRATIONS: &[Migration] = &[
    Migration {
        version: 100,
        file: "100.sql",
        sql: include_str!("100.sql"),
    },
    Migration {
        version: 101,
        file: "101.sql",
        sql: include_str!("101.sql"),
    },
    Migration {
        version: 105,
        file: "105.sql",
        sql: include_str!("105.sql"),
    },
];
```

清单是执行依据，不能通过扫描目录后按字符串排序临时生成。程序启动时必须先校验清单：

- 版本号严格递增。
- 版本号不能重复。
- 文件名与版本号对应。
- 每个 SQL 文件都能被读取。
- 最后一项是当前程序支持的数据库目标版本。

## 5. 启动升级流程

数据库启动升级只有一个入口：`Database::run_migrations`。流程如下：

1. 打开数据库，确保同一数据库同一时间只有一个升级流程。
2. 如果数据库为空，先在事务中执行 `baseline.sql` 建立主仓库 `v0.65.2` 的基线业务结构；该脚本不登记版本号。
3. 如果版本表不存在，则在迁移事务中执行清单第一项 `100.sql`，由该文件创建版本表并插入版本 `100`。
4. 读取 `schema_version.version`。
5. 在全局迁移清单中查找当前版本的索引。
6. 从命中索引的下一项开始，按清单顺序执行到最后一项。
7. 在事务中执行完整 SQL 文件；`101.sql` 及之后的文件最后自行更新 `schema_version`。
8. 提交事务后再次读取版本表，确认版本已经变成当前 SQL 文件声明的版本。
9. 所有清单项执行完成后，再次读取版本表，确认版本等于清单最后一项。

示例：

```text
数据库版本：100
迁移清单：100、101、105、110
执行顺序：101 -> 105 -> 110
最终版本：110
```

如果是全新的空数据库，则先执行 `baseline.sql`，再从第一项 `100.sql` 开始执行。如果数据库版本已经等于清单最后一项，则不执行任何迁移。

版本号不在清单中时必须停止并报错，不能猜测索引、跳过版本或直接写入最新版本。数据库版本高于程序支持的最后版本时也必须停止，禁止自动降级。

## 6. 单版本事务

每一个迁移 SQL 文件必须作为一个不可拆分的原子升级单元，独立执行一个完整事务：

```text
BEGIN IMMEDIATE
  执行 N.sql
  -- N.sql 文件内部最后执行：
  UPDATE schema_version
  SET version = N, migration_file = 'N.sql', applied_at = datetime('now')
  WHERE id = 1
COMMIT
```

要求：

- 一个 SQL 文件中的所有语句，包括表结构变更、数据变更和其中的版本表更新，必须处于同一个事务内。
- 文件中的任意一条语句失败，整个文件全部回滚，不能保留部分表结构或部分数据。
- 只有文件中的全部语句成功，事务才允许提交，版本表才允许前进。
- SQL 文件执行失败时，版本表必须保持上一个成功版本。
- 版本表更新必须是当前 SQL 文件的最后一部分，不能先更新版本表，再执行数据库变更。
- 前一个版本提交成功后，后一个版本失败，前一个版本保持成功状态。
- 下次启动从失败版本的前一个成功版本继续，重新执行失败版本。
- 迁移 SQL 应尽量保持幂等，但幂等不能替代版本清单判断。

## 7. 迁移前备份

每一份会改变数据库结构或数据的迁移，在事务开始前都必须创建一致性备份。

备份文件格式：

```text
workspaces.db.backup-before-db-migration-105-ssh-connection-status-20260811-145031.419.db
```

要求：

- 备份文件名必须包含数据库版本、变更原因和时间戳。
- 不能覆盖已有备份。
- 备份失败时不能继续执行迁移。
- 迁移成功后仍保留备份，不能自动删除。
- 版本表首次创建也属于数据库变更；没有版本表的旧数据库必须先备份。
- 每一份迁移独立备份，不能只在整个升级流程开始时备份一次后假设所有版本都可定位。

## 8. 开发阶段基线处理

当前程序仍处于开发阶段，不考虑历史正式版本数据库兼容，不实现旧数据库自动识别、跨版本补齐或降级迁移。

1. 新数据库先从 `baseline.sql` 建立主仓库 `v0.65.2` 基线，再执行 `100.sql` 登记版本 `100`。
2. 当前开发数据库首次接入版本表时，确认结构符合基线后由 `100.sql` 登记为 `100`。
3. 结构不确定的开发数据库直接重新初始化，不编写历史兼容迁移。
4. 基线建立后，所有新增数据库变更只能使用 `101.sql`、`102.sql` 等更高版本。

## 9. 失败、恢复和并发

- 启动升级失败时，程序必须给出失败版本和 SQL 文件名。
- 失败迁移的事务必须回滚，下一次启动继续重试同一版本。
- 不提供自动降级迁移。
- 需要恢复时使用对应迁移前备份，不覆盖原始数据库。
- 使用 SQLite 写事务或等效锁，防止多个程序实例同时升级同一个数据库。
- 迁移期间禁止业务连接读取一个尚未完成的中间结构。

## 10. 测试要求

每增加一个迁移版本，至少验证：

- 空数据库先执行 `baseline.sql`，再从 `100.sql` 按清单顺序升级到最新版本。
- 数据库版本为 `100` 时只执行 `100` 后面的清单项。
- 清单版本不连续时仍能按清单顺序执行。
- 单个 SQL 文件中任意一条语句失败时，验证该文件的全部语句和版本更新都已回滚。
- 已经是最新版本时不执行 SQL，也不产生迁移备份。
- 任意中间版本失败时，版本表停在失败前版本。
- 修复失败原因后重新启动，能够从失败版本继续。
- 同一数据库重复启动不会重复执行成功迁移。
- 迁移前备份文件包含正确的版本和变更原因。
- 数据库版本不在清单中时安全停止。
- 数据库版本高于程序目标版本时安全停止，不降级。
- 当前开发数据库能够建立 `100` 基线。
- 结构不确定的开发数据库能够重新初始化，不进入历史兼容流程。

## 11. 禁止做法

- 禁止使用软件版本号作为数据库版本号。
- 禁止用字符串比较或语义版本比较数据库版本。
- 禁止启动时无条件执行全部 SQL 文件。
- 禁止只执行最新 SQL 文件，跳过中间版本。
- 禁止通过 `current + 1` 推算下一版本；必须使用全局清单索引。
- 禁止由启动代码在 SQL 文件执行后单独更新 `schema_version`。
- 禁止把同一次数据库版本升级拆成多个 SQL 文件或多个数据库版本号。
- 禁止把一个版本 SQL 文件拆成多个独立事务。
- 禁止在 SQL 文件部分成功后更新版本表。
- 禁止直接把数据库版本写成最新版本来绕过迁移。
- 禁止修改已经执行过的 SQL 文件。
- 禁止迁移失败后强行更新版本表。
- 禁止在迁移清单之外执行数据库变更。
- 禁止为当前开发阶段增加历史正式版本兼容迁移。
